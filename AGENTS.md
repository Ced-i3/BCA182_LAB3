# BCA152 Laboratory Activity 3

## Project

Build an activity-recognition system for walking and running:

`RT-Spark motion sensors -> Wi-Fi/MQTT -> Python backend -> activity classifier -> SQLite/API -> responsive web dashboard`

The official assignment is `BCA180 ESP - Laboratory Activity 3.pdf`. Its firmware examples mention LSM6DSL and ISM43362; this project's actual board uses ICM20608 and RW007. Follow the hardware and framework actually present here, not those incompatible examples.

## Hardware and development environment

- Board: RT-Thread RT-Spark; MCU: STM32F407ZGT6; IMU: ICM20608; Wi-Fi: RW007.
- Windows and VS Code; official RT-Thread source at `firmware/rt-thread`, version v5.3.0.
- ARM GCC and SCons are already available in the PlatformIO package cache. Prefer these existing tools; do not install another toolchain, RT-Thread Studio, or the full RT-Thread Env package.
- The firmware BSP is `firmware/rt-thread/bsp/stm32/stm32f407-rt-spark`.

## Progress and limitations

- **Verified physical end-to-end baseline (2026-10-18):** on the RT-Spark STM32F407ZGT6, genuine ICM20608 acquisition continued at 25.0 Hz while the manually started MQTT publisher sent at approximately 5.0 messages/s over QoS 1. A 27.8-second run delivered 140 messages to a temporary MQTT observer. SQLite increased from 6 to 146 rows; all 140 new rows were for `rt-spark-001`. Flask `/api/latest`, `/api/history`, and `/health` were checked; the API returned the new readings and `mqtt_connected=true`. The board reported zero missed sampling deadlines, I²C errors, queue drops, publish failures, and reconnects. `mqtt_stream stop` returned the publisher to stopped state. The observer and database confirmed delivery. See `MQTT_STREAM_TEST.md` for the run details.
- **Firmware and sensor:** the official RT-Thread v5.3.0 RT-Spark BSP runs on the board. ICM20608 uses `swi2c2`, accelerometer range ±4 g, and gyroscope range ±500 dps. Real sensor measurements and stable stationary 25 Hz sampling have been physically verified. RW007 startup, scanning, Wi-Fi association, TCP reachability, SNTP synchronization, and MQTT test/stream delivery have also been physically verified. These tests do not establish walking/running classifier accuracy; broader movement and orientation validation remains pending.
- **Continuous MQTT publisher:** `applications/mqtt_test.c` provides `mqtt_stream start [1-25]`, `mqtt_stream stop`, and `mqtt_stream status`, while retaining `mqtt_test`. It uses a 10-sample static FIFO between the 25 Hz acquisition loop and a lower-priority publisher thread. Default output is 5 Hz via phase-accumulator decimation, without averaging. Selected samples are timestamped at acquisition using the valid SNTP-synchronized UTC clock and published to `lab3/sensors/motion` in the backend JSON schema. Streaming is disabled after boot and must be started manually after Wi-Fi and valid time are available. Phase 4A adds RAM-only shell configuration for broker host, port, and device ID; development defaults remain `192.168.1.11:1883` and `rt-spark-001`. Wi-Fi credentials are entered through the private console prompt and are not stored in source or Flash.
- **Phase 4A portable MQTT configuration:** `mqtt_config show`, `mqtt_config set broker HOST`, `mqtt_config set port PORT`, and `mqtt_config set device_id ID` configure the MQTT test, continuous publisher, and `tcp_test`. IPv4 literals and validated DNS hostnames are accepted; lwIP DNS is enabled. Port range is 1–65535; device IDs are 1–32 ASCII letters, digits, dots, underscores, or hyphens, with an alphanumeric first and last character. MQTT client IDs are derived as `bca152-<device_id>-test` and `bca152-<device_id>-stream`; each board needs its own device ID. Settings are RAM-only, revert to development defaults after reboot, and cannot be changed while streaming is active or stopping. The final ARM GCC 12.3.1/SCons 4.11.1 build succeeded without compiler warnings: CODE 262,132 B of 1 MiB (25.00%), RAM1 64,448 B of 128 KiB (49.17%), RAM2 0 B. Physical Phase 4A regression later passed: 106 genuine messages arrived at about 5.01 messages/s, SQLite increased from 146 to 252 rows, and acquisition stayed at 25 Hz with zero missed deadlines, I²C errors, publish failures, or sample drops. These results verify the MQTT configuration regression, not activity recognition.
- **Backend:** `backend/` contains the Flask API, MQTT subscriber, local broker configuration, simulated publisher, and SQLite database. Both the simulated workflow and physical board-to-broker-to-Flask/SQLite path have been exercised. The raw API stores and returns sensor readings. Phase 5 adds a separate bounded background inference worker, an additive activity prediction table, and `/api/activity/latest` and `/api/activity/history`. Raw APIs and records remain unchanged. Simulated publisher output remains separate from physical measurements.
- **ML and Phase 5:** dataset is `backend/data/archive/dataset.csv`; training scripts and model artifacts are in `backend/ml/` and `backend/models/`. The backend uses only `activity_model_corrected.joblib` with its corrected preprocessing metadata. It reports `IDLE` through an experimental rule-based detector, then maps corrected model class 0 to `WALKING` and class 1 to `RUNNING`. Unit tests cover the model contract, idle rules, windows, worker, database, and API. All hardware-facing predictions are marked experimental and **not hardware-validated**. The Run-or-Walk dataset contains one participant and undocumented sensor units/orientation; the tree is sensitive to `acceleration_y_max`. No new dataset was collected, and the model was not retrained or replaced. Labelled RT-Spark walking/running trials, calibration review, and independent performance evaluation remain required.
- **Phase 3B dependency and startup history:** the official BSP dependency packages were integrated and the BSP compiled with the existing ARM GCC 12.3.1 and SCons 4.11.1. A hardware diagnostic found lwIP's `erx` receive thread requesting priority 144 while `RT_THREAD_PRIORITY_MAX` was 32. In `components/net/lwip/port/ethernetif.c`, `RT_ETHERNETIF_THREAD_PREORITY` falls back to `0x90` when `RT_LWIP_ETHTHREAD_PRIORITY` is undefined. The BSP sets `CONFIG_RT_LWIP_ETHTHREAD_PRIORITY=12` in `.config` and `RT_LWIP_ETHTHREAD_PRIORITY 12` in generated `rtconfig.h`; TCP/IP priority is 10 and the maximum remains 32. The temporary diagnostic was removed without bypassing the scheduler assertion. Subsequent firmware startup and the streaming test completed without scheduler assertions. Historical builds reported CODE 202,736 B of 1 MiB and RAM1 59,328 B of 128 KiB for the corrected-priority image.
- **Phase 3D-A package and wiring history:** the official RW007 repository is cloned at `rw007-download`, commit `94df57f856bc2e8661022a379aa1c3d6a3bc5149` (`v2.1.0-2-g94df57f`). Its source is integrated under `firmware/rt-thread/bsp/stm32/stm32f407-rt-spark/packages/rw007-latest`. The BSP enables SPI2, PIN, Wi-Fi, lwIP 2.0.3 (TCP/UDP/DNS/DHCP), and the system workqueue used by WLAN management. The cloned package's SConscript still labels `VERSION` as `v0.0.1`; use the recorded Git commit as its source version. A historical build reported a non-fatal GCC warning about taking the address of a packed RW007 response member during scan-report handling.
- **Verified BSP RW007 wiring:** SPI2 SCK PB13, MISO PC2, MOSI PC3; CS PF10 (pin index 90), INT/BUSY PG11 (107), RESET PG15 (111). BOOT0 shares PB13/SPI2 SCK (pin index 29); BOOT1 shares PF10/CS (90). These mappings agree with the official RT-Spark schematic. The port must follow the RW007 reset/boot sequence because of the shared pins.
- **Frontend direction (2026-10-18):** native Android development was retired in favor of a responsive Next.js, TypeScript, and Tailwind CSS dashboard consuming the existing Flask REST API. The former Kotlin/Jetpack Compose source is preserved in `android-source-backup-2026-10-18.zip`; its archive entries were verified against the original files before `android/` was removed. Do not describe the classifier or walking/running recognition as hardware validated until labelled hardware tests are complete.
- **Phase 7A web dashboard (2026-10-18):** `web/` now contains the Next.js 16.4.2, React 19.3.1, TypeScript, and Tailwind CSS read-only dashboard. It uses a server-side, five-endpoint allowlisted proxy to Flask, polls about every two seconds without overlapping requests, and shows current activity only while the backend explicitly reports a fresh prediction. It separates stale sensor readings and historical predictions from live status. Nine frontend contract/freshness tests, TypeScript, ESLint, and a production build passed. The local Next.js server and proxy were checked against the running Flask backend using genuine stored data; Chrome device emulation at 390 and 320 CSS pixels showed no horizontal overflow. No new STM32 stream or live fresh classification was tested in this phase. See `web/README.md`. A public Vercel frontend still needs a separately designed, secure route to the laptop-hosted Flask backend; do not expose Flask or MQTT directly.
- **Publication source and corrected model (Phase 9C):** `firmware/project-source/` holds the pinned six-dependency manifest, complete project patches and overlays, inventory, and reconstruction instructions; the known-working `firmware/rt-thread/` remains local and untouched. An isolated reconstruction from the proposed publication files built ELF, BIN, and HEX with ARM GCC 12.3.1 and SCons 4.11.1. The project owner authorized inclusion of the existing `backend/models/activity_model_corrected.joblib`; its SHA-256 is recorded in `backend/models/README.md`. The original Run-or-Walk CSV remains excluded pending separate rights verification. Only load joblib from a trusted checkout. Fresh-copy backend and frontend software checks passed, but these do not validate activity accuracy on physical hardware.
- **Pending project work:** decide whether to add safe persistent configuration storage; verify upstream dependency downloads and the firmware build on another computer; resolve remaining third-party source and dataset redistribution questions; physically validate idle thresholds and walking/running predictions on explicitly labelled RT-Spark trials; and perform a live dashboard test during a planned STM32 stream.

## Working rules

- Inspect relevant files and Git status before changes. Preserve existing architecture and unrelated user work; make small, task-focused edits.
- Never present simulated data as real sensor readings or dataset metrics as hardware validation.
- Do not overwrite or delete datasets, models, databases, build artifacts, or other user data without explicit authorization.
- Do not install dependencies, download large archives, or change system configuration without a clear task need. Monitor disk space before any authorized large operation. Do not bypass unavailable network permissions or change global Git proxy configuration.
- Never flash the STM32 unless explicitly authorized. Do not commit, push, publish, or deploy unless explicitly requested.
- Verify changes with appropriate checks when requested or needed; report commands and actual results, distinguish source inspection/build/simulation/hardware testing, and state limitations. Do not claim tests or builds passed without evidence.
